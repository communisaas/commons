What Is Built, and What Actually Runs

Commons (commons.email) — a map of the shipped system, 2026-08

This document describes every subsystem that exists in the codebase, organised by what a person would be trying to do, and states for each one whether it works on the live site today. Where something does not work, it names the exact reason and what would change it.

The site is pre-launch. There are zero real users and zero real campaigns in the production database. That matters constantly below: some things are "off" because a switch is off, and some are "off" because there is simply nothing yet for them to show. Those are different conditions and are labelled differently.

How to read this map

Vocabulary you need first

Every technical term in this document is defined the first time it appears. These six come up everywhere, so they are here up front.

TermWhat it means
Feature flagA single true/false switch in the code that turns a feature on or off for everyone at once. Commons keeps them in one file, src/lib/config/features.ts. Flipping one is a one-line code change plus a redeploy — no database work, no new services.
RouteOne address on the site (/profile, /s/some-campaign). Each route is a small program that runs when someone visits that address.
ConvexThe database Commons uses. Unusually, the database also holds the code that reads and writes it: a query reads, a mutation writes, and an internal one can only be called by other server code, never by a browser.
Cloudflare Pages / Workers / R2 / KV / Durable Object / QueueCloudflare hosts the site. Pages serves the website itself. A Worker is a separate small program that runs on Cloudflare's network — a background service. R2 is file storage. KV is a simple key-value store for short-lived data. A Durable Object is a single coordination point that makes sure two copies of a job don't run at once. A Queue is a work list that a Worker drains. Each of these must be deployed and bound (wired to the site) separately.
CronA job that runs on a timer without anyone pressing anything — every hour, every night. Commons registers its crons in convex/crons.ts and gates them behind a setting called CRON_PROFILE.
Trust tierA number 0–5 saying how sure Commons is that you are a real, located person. Detailed in Part 5.

The status labels used throughout

On:

  • ON · verified — proven working against the live production site.
  • ON · untested — no switch blocks it and the code is complete, but nothing proves it has ever completed successfully in production.
  • ON · degraded — it runs, but a verification pass found it does something different from, or less than, what was believed.

Off, in four kinds:

TierMeaningHow to change it
OFF · hardcodedThe code returns "no" unconditionally. No setting, environment variable, or flag can reach it.Edit and redeploy the code.
OFF · flagA feature flag is false.Flip one line, redeploy.
OFF · missing prerequisiteThe code is complete but needs something external: a deployed service, a credential, a certificate, an enrolment with another company, or an operator running a command by hand.Provision the missing thing.
OFF · no callerThe code exists and would work, but nothing in the product ever invokes it. Orphaned.Wire it up, or delete it.

One correction convention

Several claims about this system were checked against the live site and found wrong. Where that happened, the corrected finding is what is written here, marked downgraded, with the original belief noted so it is not repeated.

Part 0: The single fact that shapes everything else

Two deploy pipelines exist. Only one of them runs.

.github/workflows/deploy.yml is a 5,757-line pipeline that would deploy the website and all of its background Workers, storage buckets, coordination services and queues. It requires 44 secrets named PROTECTED_*. The repository has none of them. It has never completed a run.

.github/workflows/deploy-direct.yml is 459 lines and is what actually ships. At line 228 it runs exactly one command: wrangler pages deploy. It uploads the website bundle. It deploys no Workers, no Durable Objects, no Queue consumers.

Consequently: every part of Commons that lives inside the website bundle is live. Every part that lives in a separate background service is not — unless it got there by some path outside the shipping pipeline. This single fact explains the largest broken area on the site (Part 2) and is a standing risk to one that currently works (Part 8).

Part 1: Arriving at the site as a stranger

1.1 The frame around every page — ON · degraded downgraded

What it is: the top bar with the sign-in buttons, the footer with the contact and privacy links, and the apology page shown when something breaks.

What was believed: that this frame wraps every page without exception.

What is true: the header and the error page do. **The footer does not appear on the homepage, or on any /v/ verification page.* In src/routes/+layout.svelte, the homepage branch (lines 214–220) and the verification-page branch (221–227) render the page contents with no <Footer /> at all. Live, the homepage contains zero links to /about/integrity; every other page contains one. The <footer> element visible on the homepage belongs to the landing page itself, not to the site.

This contradicts a requirement written in the footer's own source at Footer.svelte:25-26: "privacy disclosure must be discoverable from every page." It is absent from the front door.

Separately, the footer offers only four destinations — an email address, /org, and /about/integrity twice. It does not link to /browse, /developers, /spec, /directory, or /help/verification. Those five pages exist, several work perfectly, and none can be reached by clicking.

1.2 The homepage itself — ON · degraded downgraded

What it is: the front door. It returns HTTP 200, paints correctly, and is not blocked by anything.

What was believed: that it offers a visitor two things — write a campaign, or browse campaigns others wrote.

What is true: the writing affordance is real and works (see 1.3). The browsing affordance is a list component mounted in the page that renders zero cards, and the only outbound link in the served HTML goes to /org. There is no link to /browse, which exists and returns 200. So the second of the two things is a blank region, not a path.

Pre-launch with no campaigns, emptiness is expected. The overstatement is in describing a mounted-and-blank surface as an offer.

1.3 Starting to write without an account — ON · verified upgraded

What it is: an anonymous visitor types their problem into a box on the homepage, a composer opens, and their words survive a trip out to Google sign-in and back.

This was driven end to end in a real browser against production and it completes:

  1. Anonymous load renders the prompt "What needs to change?"
  2. Typing activates "Pick decision-makers"; the composer opens for a signed-out user and shows "saved just now."
  3. "Sign in to generate" redirects to Google with the draft id carried in the return address.
  4. After consent, the browser lands back on the homepage, the composer reopens by itself with the identical text, and the AI runs and asks a clarifying question.
  5. The draft, which was ownerless before, now carries an owner fingerprint — it was adopted by the account.

Correction to a common belief: drafts are not stored in src/lib/stores/guestState.svelte.ts. That store holds template interest only (slug, title, view count) and is schema-locked against holding prose. The actual draft lives under the browser storage key commons_template_drafts, written by src/lib/stores/templateDraft.ts.

One consequence, in Part 4.4: signing out deletes that draft.

1.4 Working out roughly where a visitor is — ON · verified

What it is: before you sign in, the site estimates your area from your network connection so it can show nearby campaigns, and lets you type a town to correct it.

Live, /api/location/ip-lookup returned a real city, region and coordinates; /api/location/search?q=austin returned real ranked places. This is the one genuinely data-backed anonymous feature that works today. It currently has no visible effect, because the campaign list it exists to filter is empty.

1.5 Protection against scrapers — ON · verified, narrower than believed

What it is: a counter that turns a visitor away after six requests to campaign pages in a short window, so an automated scraper cannot run up the cloud bill.

Exhausted live: eight consecutive requests produced six served, then a refusal (HTTP 429). Window is 10 seconds, limit 6. Malformed campaign addresses (/s/A, /s/UPPER_CASE!!) are refused before any storage is touched.

Two limits worth carrying:

  • Coverage is exactly two address shapes — /s/:slug and /s/:slug/og-image. Deeper addresses are excluded, and they are not inert: /s/valid-slug-here/debate/abc returns HTTP 500 with no rate-limit headers at all, repeatedly. Something is doing unmetered server work on an unprotected path.
  • The counter is per server instance, not global. A second Cloudflare instance keeps its own count. This is the documented design; the Cloudflare firewall rule remains the real cross-instance boundary at launch.

1.6 The database spend ceiling — ON · verified

What it is: before any page is allowed to ask the database a question, it must draw down a shared allowance, so a traffic spike cannot blow past the free tier.

Proven indirectly but soundly: /directory returns the specific message "Organization directory is being prepared," which is only reachable after a database query actually executed. Had the meter been unreachable, the failure would have carried a different, generic message. The meter is present, reachable, and granting.

Standing risk: the meter service (commons-convex-work-budget) is a Worker, and Workers are only deployed by the pipeline that has never run (Part 0). It exists in production by some path outside the shipping pipeline. If it were ever lost or redeployed wrong, every data-backed anonymous page becomes a 503.

1.7 Crash reporting — ON · verified, one figure mislabelled

What it is: when a page breaks, the failure is sent to a monitoring service and the visitor is shown a short reference code to quote to support.

Proven by pulling the body of a live 500: the page renders Reference: 4ec0-0d0f-ce07, a real shortened monitoring event id. The capture ran and returned an id.

Correction: "sampling is 10%" refers to performance traces, not error capture. Errors go up unsampled.

One failure mode outside this net: one early request returned a 17-byte body, error code: 1101 — a raw Cloudflare exception that bypasses the site's code entirely. No error page, no reference code, invisible to this path. It did not reproduce.

1.9 Search-engine instructions — OFF · missing prerequisite

There is no robots.txt and no sitemap.xml owned by this repository. The robots file being served is Cloudflare's generic managed default about AI-training signals. /sitemap.xml returns 404. Low urgency while the public listing is empty — there is nothing to index yet.

Part 2: Finding a campaign to join — the largest dark area

This is the half of the product a stranger would use, and it is entirely non-functional on the live site.

2.1 How it is supposed to work

Commons does not build campaign pages from the live database on each visit. A background job reads the database, bakes the public campaign list and every individual campaign page into files in Cloudflare R2 storage, and writes one small index file — a manifest — that says which files are current. Every public surface reads the manifest first. Readers are explicitly forbidden from falling back to the database if the manifest is missing; that rule is enforced by a guard file whose whole job is to throw an error rather than let a page quietly query the database directly.

2.2 What has actually happened: the manifest has never been written

Status: OFF · missing prerequisite.

At src/lib/server/public-template-queries.ts:683 the code says: if the manifest does not report itself ready, throw. It is not ready. It has never been written.

The reason traces straight back to Part 0. The job that writes it runs as three separate Cloudflare services:

ServiceWhat it does
commons-public-discovery-manifest-gateA Durable Object — the coordination point that stops two copies of the publish job running at once.
commons-public-discovery-manifest cron WorkerThe timer that triggers the publish.
commons-public-template-og queue consumerRenders the social-share picture for each campaign.

None of the three is deployed, because only deploy.yml deploys Workers and deploy.yml has never run. Additionally, the R2 bucket commons-public-discovery-cache must be provisioned and a shared secret (DISCOVERY_MANIFEST_REFRESH_SECRET) set in three places, and at least one published campaign must exist in the production database for there to be anything to bake.

2.3 Everything downstream

Every entry below is OFF · missing prerequisite, and every one of them has the same prerequisite: the manifest. None of them is individually broken.

2.4 The debate page — OFF · flag, on top of the above

/s/[slug]/debate/[debateId] shows a structured argument attached to a campaign with scored positions. FEATURES.DEBATE is false, which hides every entry point to it. The page's own loader has no flag check, but it sits inside the broken campaign layout, so it returns 500 today regardless.

A knock-on worth knowing: FEATURES.STANCE_POSITIONS is true, but it has no public surface at all, because every place it renders is nested inside the DEBATE check. A flag being on does not mean a user can see it.

2.5 The congressional filter — OFF · flag

FEATURES.CONGRESSIONAL is derived from a build-time variable (VITE_CONGRESSIONAL === '1') and is false in the shipped bundle. Any campaign addressed to Congress is therefore hidden from the homepage and /browse and returns "not found" on its own page. This is deliberate, pending the congressional launch. It is invisible to visitors right now because the listing is empty either way.

Part 3: Checking whether a claim is real

Three public pages exist so that an outsider — a congressional staffer, a journalist — can verify that a Commons campaign was backed by real, located people. This is the product's entire claim to credibility. Two of the three are broken, and both break the same way.

3.1 The mechanism behind all of it

In Convex, asking the database for a record by id (ctx.db.get(x)) throws an error when handed a string that isn't a validly-formatted database id. It does not politely return "not found." Some queries wrap that in a guard; the verification queries do not.

The contrast is in the same codebase. convex/campaigns.ts:470-474 wraps the lookup in a guard and returns nothing → /og/campaign/xyz gives a clean 404. convex/verify.ts:90 does the identical lookup unguarded → /verify/receipt/abc123 gives a 500.

None of this was caught by tests, because tests hand these functions well-formed ids.

3.2 /v/[hash] — public verification certificate — ON · verified

What it is: a shareable page proving a campaign's messages came from real, located people — how many were verified, which districts they covered, no names. Counts below 5 people (or 3 districts) are deliberately hidden to protect participants.

It works. Unknown codes return a clean 404, confirmed with both a short string and a real 64-character hash.

Evidence correction: the belief that this "proves two database lookups ran" is wrong. The first lookup declares a strictly-typed campaign id; a hash fails argument validation and throws, silently swallowed by an empty catch block. Only the second lookup — a string index query — actually executes. One lookup ran, not two.

3.3 /verify/[hash] — the staffer credential check — OFF, in effect downgraded

What it is: the page a congressional staffer opens to check one delivery or one person's district credential: genuine, current, revoked?

What was believed: that it never errors — an unknown code produces a polite "credential not found" page.

What is true: the claim is inverted. It never succeeds.

  • The test that produced the polite page used a 6-character code, which trips a length guard and renders "Invalid verification link" without ever reaching the database.
  • Fed input of the correct shape — a 64-character hex credential hash, the exact format the system enforces — the live site returns HTTP 200 "Verification temporarily unavailable." That is the generic error handler, not a not-found state.

Cause: verify.getDelivery performs an unguarded id lookup. A 64-hex hash is never a valid database id, so it throws. Because a single try-block wraps all three lookups, the campaign and credential paths beneath it are unreachable for the exact input format the page exists to accept. A staffer pasting a real credential hash gets a generic error.

3.4 /verify/receipt/[id] — accountability receipt — OFF · broken downgraded

What it is: turns a delivery record into readable prose — who was contacted, what they did afterwards, how confidently the two are linked. The "did this change anything" surface.

What was believed: unknown ids return 404.

What is true: the live site returns HTTP 500, for short ids and for correctly-shaped ids alike. Same unguarded lookup, and this page has no catch block at all, so the error escapes as a server crash.

The feature flag (FEATURES.ACCOUNTABILITY) does pass. The page is switched on and broken.

(A footnote: /verify/receipt with no id at all returns 200 — because "receipt" is 7 characters, under the 8-character floor, so it renders "Invalid verification link." Right answer, accidental reason.)

3.5 Summary of Part 3

4.4 Sign out — ON · verified, with three consequences

Clicking the real sign-out button and inspecting the browser afterwards: local storage completely emptied, the address and key stores deleted, and the site no longer authenticated.

Three things the plain description misses:

  1. It destroys your saved drafts. The wipe removes commons_template_drafts — the very draft the guest flow works so hard to preserve through sign-in. Plausibly intended; not what "wipes anything sensitive" implies.
  2. One cookie survives. oauth_completion is not protected from page scripts and remains readable after logout, carrying which provider you used and the id of the draft you were writing. On the shared computer this feature exists to protect, the next person can read it.
  3. Server-side revocation is best-effort and unproven. The call that deletes the session record on the server is wrapped in a catch-and-continue; the cookie is deleted either way. The observed behaviour proves the cookie is gone. It does not prove the database row was deleted.

4.5 Email verification — ON · degraded downgraded

What was believed: Commons never sends a confirmation email; it trusts Google's or LinkedIn's own statement that they already verified your address, and records that as fact. Having a verified email is what lifts you off the bottom trust rung.

What is true: it never reads their statement.

  • The callback computes emailVerified = userData.emailVerified !== false — meaning absent counts as verified.
  • Google's data-reshaping function returns id, email, name, avatar. No verified field.
  • LinkedIn's returns id, email, name, avatar. No verified field.
  • Neither provider's response-shape check even looks for one.

Google's and LinkedIn's responses both do carry a verified flag. Both are discarded. The value reaching the account-creation step is undefined, which the test converts to true unconditionally. Every Google and LinkedIn signup receives trust score 100 and trust tier 1 regardless of what the provider actually said — and would continue to, even if a provider explicitly reported the email as unverified.

Only two providers ever set the flag honestly, and neither is a live sign-in button: Twitter derives it from whether an email came back at all; Coinbase hardcodes true on a know-your-customer rationale.

There is no standalone confirm-your-email flow anywhere in the codebase. If a provider that does not verify emails were ever added, there is no fallback.

Given that email is the documented anti-fake-account control, this is the substantive finding of Part 4.

4.6 The two developer backdoors

SubsystemStatusDetail
Test-only backdoor loginOFF · flagLets automated tests become a signed-in user without clicking through Google. Requires both ENABLE_DEV_LOGIN=1 and ENVIRONMENT=test; neither is set in production. Deliberately double-locked.

4.7 Account deletion and data export — OFF · no caller

There is no way for a user to delete their Commons account, and no way to download what the site holds about them. No route, no page, no database function — searches for every plausible name return nothing. Only per-message opt-outs exist (/unsubscribe, /do-not-contact).

Nothing to flip. This has to be written: a confirmation interface, a mutation that erases the user record plus their district credentials, sessions and address vault, and an export endpoint.

Part 5: Proving who and where you are

This is the deepest part of the system and where most of the engineering went.

5.1 The trust ladder — ON · degraded downgraded

What it is: a number saying how sure Commons is of your identity, which a recipient's office can use to weight your message.

The designed ladder: 0 guest, 1 signed in, 2 address confirmed, 3 identity document checked, 4 passport, 5 government digital driver's licence.

What is actually derivable:

RungDesigned meaningReality
0GuestNever returned. The code says so explicitly; the function's final statement returns 1. Any signed-in user floors at 1.
1Signed inReturned — but see 4.5: granted unconditionally, not on provider evidence.
2Address confirmedWorks (5.3–5.4).
3Identity document checkedWorks in principle.
4PassportNever returned. No branch in the code produces a 4. There is no passport verification path.
5Government digital licenceRequires the mobile-licence lane (5.7), which has an unverified production prerequisite.

So the live ladder is 1, 2, 3 — and 5 if and only if a production certificate is installed. Two of six rungs are structurally dead.

Citation correction: the ladder is not computed "on every request." The line often cited is an import. The single call site sits inside the block that assembles the signed-in user object — so it runs per authenticated request, never for a guest.

5.2 The "prove yourself to continue" panel — ON · verified, narrower than it sounds

What it is: when an action needs more proof than you have, this panel appears, shows the ladder, and routes you to the next step — address, government ID, or account recovery. It honestly tells you when a required step is unavailable rather than inventing a next rung.

Both mount points confirmed (the send flow and the profile page). Its "coming soon" branch is currently inactive because the Android licence lane is enabled.

Narrowing: both mounts are wrapped in a signed-in check. A guest never sees this panel — the sign-in wall comes first. "Prove yourself to continue" reads as guest-facing and is not.

5.3 Address → congressional district — ON · verified, stronger than claimed

What it is: you type your street address; the site works out which congressional district you live in. Critically, the address is matched against map data files Commons publishes itself — not sent to Google or any commercial address service. This is a hard privacy constraint of the project.

Live: the map manifest returns 200, the district index returns 200 at 16.4 MB, and address files return 200.

One thing the original claim asserted without checking: the map service sends a permissive cross-origin header, so a browser can actually fetch those files directly. It can. That is what makes client-side district calculation possible rather than theoretical.

The deploy pipeline hard-fails if the map URL is unset, which is a real safeguard.

Coverage boundary: the system declares 10 of 24 possible district types, and only congressional is nationally complete. Live reach is congressional-only.

5.4 The address verification wizard (Tier 2) — ON · verified

What it is: the step-by-step panel that takes your address, confirms your district, and turns it into a badge on your account. Your browser does the district calculation itself and sends the server only a scrambled summary — the plain address never leaves your machine on this path.

Its flag cannot be false in the shipped bundle: the only way to force it off throws an error at build time in a production build. Two independent real entry points confirmed: the send flow and the profile page.

5.5 District credential issuance — ON · verified

What it is: once your district is confirmed, the server mints a small signed document saying "this person lives in district X" — with no record of where in the district. That document is what later proves to a congressional office that you are a real constituent, and it lifts you to trust tier 2.

Live, the endpoint returns "authentication required" rather than "not found," confirming it is deployed behind the session gate only.

The anti-forgery mechanism is real: supplying coordinates without a valid server-issued, cryptographically-signed address token is rejected with a specific error, so a browser cannot invent a location. (The enforcement is at lines 366–392 of the endpoint, not the interface declarations at 80–92 that are usually cited.)

5.10 The second, separate ladder: engagement — OFF

What it is: distinct from trust. Trust says how sure we are who you are; engagement says how much you have actually done. It is meant to show a decision-maker you are a sustained participant, not a one-off.

Status: OFF. The write that would raise it is guarded on a condition combining a user id and a verified flag, and the surrounding conditions are not met on the live system. The cryptographic version reads from the absent write relay (5.9) and is explicitly non-blocking — it returns tier-zero defaults on any failure, so it will silently read as zero indefinitely rather than erroring. Nothing about this surfaces as a fault; it just always says zero.

Related — the backfill job: OFF · no caller. A maintenance routine exists to recalculate everyone's engagement score in bulk, for example after changing the formula. It is an internal-only mutation, absent from the cron list, and has zero invocations anywhere in the codebase. Nothing triggers it.

5.11 Your own record of what you sent — OFF · missing prerequisite downgraded

/profile/receipts is the list of messages you have delivered, each with a receipt you can show someone.

What was believed: it is simply unpopulated because there are no users yet.

What is true: it is structurally empty, for two reasons the original assessment missed.

  1. The underlying query calls a readiness check that throws unless a migration record satisfies eight conditions. That record is created only by two internal mutations that are not in the cron list and have zero callers in the codebase — the only invocation documented anywhere is a manual operator command in a deployment guide. Nothing runs it automatically.
  2. The page does not wrap its query in error handling, so if that check fires the page is a 500, not an empty state.

The page is saved from that 500 today only by an earlier escape hatch: the query returns an empty list for any user without an identity commitment. And the only thing that writes an identity commitment is the mobile-licence path — a Tier-2 district-verified user never gets one.

Net effect: today it renders an empty list for everyone, and would 500 for the first mobile-licence-verified user unless an operator had manually run the migration.

5.12 Revocation — OFF · missing prerequisite

What it is: when you move house or re-verify, your old district badge must be marked cancelled so it cannot be reused. The permanent cancellation is meant to be written to a public blockchain ledger so anyone can independently confirm a badge was withdrawn.

Two separate stops:

  1. The database function returns early — leaving the credential in a "pending" state — unless an internal URL and internal secret are both set in the Convex environment.
  2. Even past that, the blockchain client requires a revocation registry contract address, which is absent from every environment file. Only a district-gate address and a testnet endpoint are configured.

Important: the database-side revocation still works. Old badges are marked cancelled locally. What is missing is the independently-checkable public record.

5.13 Delegation — OFF · hardcoded

/settings/delegation was planned as the page where you grant a software assistant permission to take civic actions for you within limits you set — which issues, how many per day, what needs your review.

Three layers of off, in order of hardness:

  1. The page loader unconditionally throws a 404. Verified live.
  2. The backing database functions are matching tombstones — thirteen sites that only throw a not-launched error. They contain no real implementation.
  3. FEATURES.DELEGATION is false.

Flipping the flag would achieve nothing; the reads and writes have to be built.

This is also the only route under /settings. There is no settings landing page at all.

Part 10: The four things this map is really saying

1. The brochure works; the product does not. Every static, read-only public page — /about/integrity, /help/verification, /developers, /spec, the drawn-in-code share cards — is healthy and verified. Every page that needs campaign data is dark, because one background job that bakes the campaign files has never run, because the pipeline that would deploy it has never run.

2. The verification surfaces are the weak spot, and they are the entire credibility claim. Three pages exist so an outsider can check that a campaign was real. One works. One returns a generic error for the exact input it was built to accept. One returns a server crash. All three failures trace to one two-line habit — calling the database's id lookup on a caller-supplied string without guarding it — and the correct pattern already exists elsewhere in the same codebase. Tests never caught it because tests pass well-formed ids.

3. Two claimed safeguards are not doing what they are described as doing. Email verification does not read what Google or LinkedIn actually said; it defaults to "verified" unconditionally, and would keep doing so if a provider explicitly said otherwise. The duplicate-person ceiling gates address verification rather than signup, and is bypassed by plus-addressing. Email is the documented anti-fake-account control.

4. Two of the six trust rungs cannot be reached at all, and the top one depends on a certificate whose presence cannot be confirmed from the repository — and whose absence surfaces to a user as an opaque server error rather than a diagnostic. The live ladder is three rungs wide, not six.
